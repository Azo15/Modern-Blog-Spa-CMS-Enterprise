# Notification bell

Work is isolated on `feature/notification-bell` in four commits; master/main are unchanged. Database migration: `20261023211840_AddNotificationSystem`. A generated idempotent SQL Server script is in `docs/deployment/NotificationSystem.sql`. Apply through the normal migration process before running the feature (the application already migrates its database on startup when configured). Back up the production database as usual. No production publish or database change was performed during development.

Each active Admin/Staff has a separate durable row for an event, with unique `(RecipientUserId, EventKey)` protection. Read state is per recipient. Notifications are ordered by database ID and the dropdown shows the latest ten. Full history is paginated at 25 per page. A bulk read includes only IDs at or below the response snapshot's LatestId, preserving later arrivals. Event links come from a fixed server-side type-to-route mapping. No exception text, SMTP credentials, job arguments or raw HTML are stored in notification messages.

Contact submissions (including newsletter interest using the common submission service) and appointments publish immediately after their durable source record commits. Notification failures do not undo customer requests. The recurring `recover-notifications` Hangfire job runs every minute and repairs missing events from durable source rows, 100 records per category per run, oldest first. It creates a single reminder per message once it is over 24 hours old and unread or unanswered. Pending email outboxes with LastError create one alert per delivery. Already-sent emails are excluded. Existing source rows are gradually backfilled; later staff accounts do not automatically receive a copy of an already-published historical event.

A global Hangfire apply-state filter creates a deduplicated generic alert when FailedState is actually applied (after AutomaticRetry elects its final state), including jobs other than mail. This callback is best effort: if the notification database itself is unavailable, it logs only the error type and leaves the failure visible in Hangfire. Mail/source event repair continues through the recurring job. A retry of the same event does not reset an already-read notification or flood the list. Source completion does not erase notification history.

The existing NotificationHub keeps its authorized legacy Managers group and adds a server-selected personal group. There is no client method for joining arbitrary groups. DB membership, active state and lockout are checked on connection and before personal count pushes; a customer or revoked role cannot fetch notification data. NotificationsChanged carries only the recipient's current unread count. Source data and lists are fetched by that authenticated user through scoped endpoints. Role/active checks are performed against the database for every endpoint, including stale cookies. Legacy manager toast behavior is retained.

Endpoints: GET `/admin/notifications`, `/admin/notifications/list`, `/admin/notifications/count`; POST `/admin/notifications/read` (id) and `/admin/notifications/read-all` (throughId). Read mutations require antiforgery validation and ownership. List sizes are capped at 50. Responses are not cached. The bell uses the shared XspaAjax helper, safe text nodes, same-origin links, reduced-motion styling, keyboard focus, accessible count labels, opt-in existing sounds and no reload for read actions. SignalR reconnect/visibility events refresh the list; a visible tab polls every 30 seconds as fallback. Clicking a record naturally navigates to its detail page after marking it read.

Validation covers schema uniqueness, source creation/recovery, ownership, snapshot bulk reads, role revocation, SignalR personal groups/counts, terminal Hangfire failures, encoded page content and JavaScript behavior. Live multi-browser delivery and production hosting deployment still require the normal release step.
