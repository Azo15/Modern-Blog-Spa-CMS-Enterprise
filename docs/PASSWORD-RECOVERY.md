# XSPA password recovery

Routes: GET/POST `/dashboard/sifremi-unuttum` and `/dashboard/sifre-sifirla`. Both mutation forms require antiforgery tokens. Recovery requests and reset attempts are each limited to five per IP per 15-minute process-local window. Valid forgot-password requests have the same generic confirmation for existing, inactive and missing accounts, including SMTP failures; transport timing is not constant-time. SMTP errors log only their type, without address, link or token.

Identity generates protected password reset tokens. Links carry a base64url representation and expire after one hour. Password changes invalidate reuse through the Identity security stamp, and a token cannot reset another user. Reset does not sign the user in or activate inactive accounts. Normal Identity password policy applies, plus a 6–128 character UI/server length bound. Authentication cookies remain subject to the configured security-stamp validation interval.

Mail uses the existing authenticated TLS SMTP transport with the selected sender. It is sent during the request with a 90-second deadline; these sensitive token-bearing messages are not stored in Hangfire arguments. There is no automatic delivery retry. The user can request a fresh link after fixing SMTP. This does not change the delivery/recovery behavior of contact replies.

`Authentication:PublicOrigin` optionally sets the canonical HTTPS origin for links; default is `https://xspawellness.runasp.net`. Request Host headers are never used for the reset destination. Keep `DataProtection:KeysPath` configured to a persistent private directory outside wwwroot; otherwise restarting a host with ephemeral keys invalidates issued links and saved SMTP credentials. No database migration is required.

Google auto-linking now explicitly trusts Google's verified email assertion for matching local accounts, including manager accounts, as requested. Email alone is insufficient: the trusted verification claim must be true. Account status, lockout and Identity two-factor checks remain enforced; no roles are added or changed. New users still complete the telephone and privacy-notice registration form.

Recovery views use the shared login layout, semantic labels, validation announcements, new-password autocomplete, keyboard focus styling and the existing reduced-motion support. Reset pages disable response caching and send Referrer-Policy: no-referrer.

## Persistent SMTP protection recovery (22 October 2026)

Production and Staging now default to `.xspa-data-protection` beside the application content root, outside the directory replaced by publication. For MonsterASP's `D:\Sites\site99770\wwwroot` application root this resolves to `D:\Sites\site99770\.xspa-data-protection`. Existing `DataProtection:KeysPath` overrides remain supported, but paths inside the application directory are rejected to avoid exposing or publishing keys. Development/Testing retain their existing default behavior unless an explicit external path is supplied.

The hosting application identity must have read/write access to that private directory. Preserve it through deployments and backups; restrict it to the site identity and administrators. File-system key persistence uses the standard framework repository and does not itself add encryption of master key files at rest; private filesystem permissions and hosting isolation are required. Use a supported certificate-based key encryption provider when the environment requires additional at-rest encryption. No hardcoded key or plaintext SMTP storage is introduced. Failure to create the private directory is a deployment configuration error and must be resolved rather than silently falling back to ephemeral keys.

Old ciphertext cannot be recovered if its original ephemeral key is already lost. After publishing this fix, re-enter the Gmail app password once in SMTP settings and save it yourself. Restart once and verify a test mail still sends; then submit the intended reply once. Saving unrelated settings with a blank password preserves the stored ciphertext; unreadable saved passwords produce a validation notice instead of an unhandled exception. No existing replies are bulk resent and no schema migration is necessary.

## Google-only account recovery and repeated registration (23 October 2026)

The GET/POST recovery actions were already present. They now distinguish Google-only accounts internally without exposing that account classification in the public confirmation. The visible form explains Google sign-in to everyone and includes the existing CSRF-protected Google button. Google-only users receive a dedicated email explaining that no separate local password exists; the same protected one-use reset link can establish their first local password if desired. Setting that password preserves the Google login and existing role. Users with passwords receive the standard reset email. Both paths use the existing SMTP service and have the same generic browser confirmation.

Google user-info is explicitly pinned to Google's v3 endpoint with email/profile scopes and the email_verified mapping. A linked provider key can authenticate even if the account's email later changes. An unlinked email still needs a valid trusted verified-email claim. Re-posting an old Google registration form for an existing account redirects to the common callback rather than displaying an already-registered error. It never bypasses disabled-account, lockout or Identity two-factor checks.
